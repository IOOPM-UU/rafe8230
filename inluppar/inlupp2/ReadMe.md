# Inlupp 2 — Simple webstore backend

Rasmus Ferngren - (rafe8230)

A small webstore backend in C with a text user interface. It keeps track of
merchandise, their storage locations and stock, and shopping carts. It is built
on the generic hash table and linked list from Inlupp 1.

All commands below are run from `inluppar/inlupp2/`.

## Building and testing

Requirements: `gcc`, CUnit (`-lcunit`), `valgrind` and `gcov` (comes with gcc).

```bash
make            # Compiles all files
make test       # Builds and runs all tests
make clean      # Removes all binaries and generated files
```

Other targets:


## Using the program

Build and start the program with:

```bash
make run
```

or, after `make`, run `./binaries/shop` directly. No other files need to be
present: the program starts with an empty database and nothing is saved
when it quits.

The program shows a menu and reads one command at a time: 

| Key | Command |
|---|---|
| `A` | Add merchandise (name, description, price) |
| `L` | List merchandise |
| `D` | Remove merchandise |
| `E` | Edit merchandise (name, description, price) |
| `S` | Show stock (storage locations and amounts) |
| `P` | Replenish stock on a storage location |
| `C` | Create a cart |
| `R` | Remove a cart |
| `+` | Add merchandise to a cart |
| `-` | Remove merchandise from a cart |
| `=` | Calculate the cost of a cart |
| `O` | Check out a cart |
| `Q` | Quit |

Storage locations are written as one letter followed by two digits, e.g. `A25`.
Merch names are case sensitive. Prices are entered and stored in öre.

## Known limitations, cheats and dodges

Remaining simplifications and deals, kept here so nothing is hidden:

- **Cart ids are not returned.** `ioopm_cart_create` does not hand back the id
  of the new cart. The UI relies on the invariant that the i:th cart created
  has id i (see *Invariants*).
- **Linear search for cart keys.** `cart_stored_key` scans a whole cart to find
  the key string to free, because the hash table's `remove` does not return
  the stored key. Fine for small carts, O(n) instead of O(1).
- **No profiling.** `gprof` was not used.

## Database design

The backend (`buissness_logic/db.c`) keeps the entire database inside one
struct, `ioopm_data_base_t`, built from the hash table and linked list from
Inlupp 1.

### Overview

```
name_id_ht   "Apple" ──► 3                 (merch name → merch id)
ht_s         3 ──► merch_t                 (merch id → merch)
                     ├─ id, name, desc, price
                     └─ list ──► [ A10: 5 ] ──► [ B04: 2 ]   (shelves)
ht_n         "A10" ──► 3                   (shelf name → id of the merch stored there)
carts        1 ──► { "Apple": 2, "Pear": 1 }   (cart id → cart)
```

### Tables

| Field | Key → value | Purpose |
|---|---|---|
| `name_id_ht` | merch name → merch id | Find a merch from the name the user types |
| `ht_s` | merch id → `merch_t *` | All information about a merch |
| `ht_n` | shelf name → merch id | Find what is stored on a storage location |
| `carts` | cart id → cart (hash table) | All shopping carts |
| `next_id` | | Next merch id to hand out |
| `next_cart_id` | | Next cart id to hand out |

Each **merch** (`merch_t`) holds an internal id, its name, description,
price (in öre) and a linked list of its storage locations (`ioopm_shelf_t`:
shelf name and amount). The stock of a merch is the sum of the amounts on its
shelves.

Each **cart** is a hash table mapping merch names to quantities (always > 0).

### Why merch have an internal id

Merch are stored under an id instead of their name. Renaming a merch (`E`)
only updates `name_id_ht` and the merch itself; the merch keeps its id, so
`ht_s` and `ht_n` do not have to change. The id is never shown to the user.
Looking up a `merch_t` stays O(1).

### Invariants

The backend keeps these rules true after every operation:

- **No empty storage locations.** A shelf always holds at least one item. When
  checkout empties a shelf, it is removed from the merch's list and from `ht_n`.
  The merch itself stays, with stock 0.
- **One merch per storage location.** `ht_n` is used to reject replenishing a
  shelf that already holds another merch.
- **All orders are fulfillable.** The total quantity of a merch in *all* carts
  never exceeds its stock. Adding to a cart is refused (`CART_NOT_ENOUGH_STOCK`)
  if it would break this, so every cart can always be checked out.
- **Cart ids are never reused.** Ids start at 1 and come from `next_cart_id`,
  so the i:th cart created always has id i, even after carts are removed.
- **Carts follow their merch.** Renaming a merch renames it in every cart;
  removing a merch removes it from every cart.

### Memory ownership

- The database owns every merch, shelf and string stored in it, and frees
  them in `ioopm_db_destroy`.
- Each cart owns its own copy of every merch name it uses as a key, so carts
  and merch never share a string. Keys are freed when an entry reaches
  quantity 0, when the cart is removed or checked out, and when the database
  is destroyed.
- `ioopm_db_add_item`, `ioopm_db_edit_merch` and
  `ioopm_cart_increase_quantity` take ownership of the strings passed to
  them only when they return `DB_OK`. On any other result the caller still
  owns them and must free them.
- All other functions only borrow the strings passed to them.

## Design decisions

### Layers
The program is split into the four modules from the spec. Dependencies only
point downward: `user_interface` → `buissness_logic` → `generic_utils` /
`generic_data_structs`. The backend never reads input or prints; every backend
function returns an `ioopm_db_result_t` and the UI decides which message to
show. This lets the backend be tested with CUnit without any user input.

### Carts store merch names, not ids
A cart maps merch name → quantity. The trade-off is that renaming (`E`) and
removing (`D`) a merch must also update every cart, which
`carts_update_merch` does. Using ids as cart keys would avoid that, but
names keep the cart code and the cost calculation simple.

### "All orders must be fulfillable" is checked when adding to a cart
Before adding to a cart, the backend sums the quantity of that merch in *all*
carts and refuses the add if it would exceed the stock. The sum is recomputed
on every add instead of being stored in a counter, so there is no extra state
that has to be kept in sync on remove, destroy and checkout. Because of this
check, checkout can never fail for lack of stock.

### Stock reaching 0
When checkout empties a storage location, the location is removed. The merch
itself is kept with stock 0, since only `D` removes a merch. Checkout takes
items from the merch's storage locations in list order.

### Edge cases the spec leaves open
| Situation | Behaviour |
|---|---|
| Add 0 items to a cart | Refused (`DB_INVALID_AMOUNT`) |
| Remove 0 items from a cart | Allowed, nothing changes ("zero or more items") |
| Remove more items than the cart holds | Refused (`DB_INVALID_AMOUNT`) |
| A merch's quantity in a cart reaches 0 | The merch is removed from the cart |
| Calculate cost of an empty cart | `CART_EMPTY` |
| Check out an empty cart | Refused (`CART_EMPTY`), the cart remains |
| Merch names | Case sensitive: "Apple" and "apple" are different merch |

### Prices
Prices are stored as integers in öre to avoid floating point rounding.
